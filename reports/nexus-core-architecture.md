# Ядро Нексуса — архитектура и контракт

Основа: `feature/random-deal-status-tooltips`, 28d8a68. Реализация: `feature/nexus-core`.

## Данные матча

Новых таблиц и SQL-миграций не требуется: используется приватный JSON `private.matches.state`.

```json
{
  "rules": {
    "abilities": true,
    "counters": true,
    "variants": "существующий объект параметров",
    "nexusCoreEnabled": true,
    "coreVersion": 1,
    "coreProfile": "balanced"
  },
  "hands": {"1": "13 серверных карт", "2": "13 серверных карт"},
  "corePreparations": {
    "1": {
      "round": 1,
      "phase": "core_selected",
      "placements": "три линии, только id шести пар",
      "coreCardId": "♥A"
    }
  },
  "coreExclusions": {"1": ["♦7"], "2": ["♣2"]}
}
```

`coreExclusions` — карты, исключённые при формировании **текущей** руки. После боя они заменяются только что сожжёнными; старые возвращаются в доступную колоду. Они не складываются в постоянное кладбище. Дескриптор усиления не сохраняется как доверенные клиентские числа: сервер каждый раз берёт масть и достоинство из своей руки.

## Фазы одного игрока

`placement → nexus_core → core_selected → ready → resolution → placement следующего раунда`.

1. Игрок ставит пары. На двенадцатой карте клиент автоматически вызывает `prepare-core` без карты Ядра. Если сеть недоступна, есть повторное открытие нажатием на Ядро.
2. Сервер под `FOR UPDATE` проверяет 12 уникальных id из руки из 13 карт и фиксирует раскладку. С этого момента пары заморожены. Можно восстановить эту стадию через F5.
3. Второй `prepare-core` с `coreCardId` проверяет единственную оставшуюся карту. Выбор фиксируется, повтор того же запроса идемпотентен; изменение пар/карты запрещено. В этой версии отмены подтверждения нет у обеих сторон.
4. Обычная кнопка «Готово» вызывает `submit-turn`. Сервер повторяет валидацию и сравнение с зафиксированной подготовкой. До готовности второго игрока боя нет.
5. Расчёт и следующая раздача — в одной транзакции. Карты Ядра материализуются из серверной руки, затем передаются общему движку. Бонусы действуют только при `nexusCoreEnabled=true`.
6. Отчёт сохраняет публичные `cores.a/cores.b`; только теперь они доступны сопернику. Текущие подготовки очищаются. В следующей руке ровно 13 карт с персональным исключением последнего сжигания.

`get-state` возвращает `me.preparation`, `me.phase`, `me.core` и свои исключения только владельцу. Соперник до отчёта получает только существующие флаги готовности. Realtime передаёт номер версии, не приватные карты. Источник истины — сервер; localStorage хранит только id матча.

## Бой и AI

Сохранён порядок: очищение/лечение стартовой фазы → поджог → фиксация целей → основные атаки обеих сторон → вторичные способности → перенос статусов. Уникальные бонусы Ядра встраиваются внутрь исходного триггера **после проверки контрстихии**. Исходные `pairStats`, HP, комбинации и направленность контрстихий не меняются.

Использованы исправления предыдущего аудита: закрепление целей фазы, устранение дублирования контр-Воды, корректная огненная ответка по щиту, правильный знак оценки угроз AI и различение ролей пар.

`chooseCorePlan` перебирает сохранение каждой из 13 карт для Ядра; для оставшихся двенадцати строится допустимая раскладка. Сравниваются общие сэмплы скрытой руки противника и два раунда общим движком. Следующая собственная раздача исключает сожжённую карту; её RNG отделён от эффектов текущего боя. В прогнозе следующего хода используется тот же DP-подбор пар, а не ослабленная greedy-модель. Слабый априорный приоритет качества пар (0,25 от суммы рабочих характеристик) сдерживает переоценку краткосрочных бонусов. При исчерпании бюджета первым рассматривается оптимизированный допустимый fallback, а не автоматически старшая карта. Это ограниченная MC-оценка, не доказательство глобального оптимума. Бюджет проверки — 800 мс, после предварительного построения модели; это мягкая отсечка, не жёсткая real-time гарантия. В эксперименте отсечка отключена для воспроизводимости.

## Совместимость и выпуск

У старых матчей отсутствие `rules.nexusCoreEnabled` означает **false**: 14 карт, прежний submit без Ядра. Новые комнаты на feature-ветке по умолчанию включают Ядро; `create-room({nexusCoreEnabled:false})` сохраняет режим A. Флаг и rules.variants сохраняются при входе второго игрока и реванше. Подтверждение бота при реванше автоматическое.

Production не обновлялся. Для отдельного согласованного выпуска потребуются согласованные версии клиента и функций `create-room`, `join-room`, `rematch`, `prepare-core`, `submit-turn`, `get-state`. Выкатывать один клиент с обязательным Ядром без серверной части нельзя. Временные локальные матчи для демонстрации живут только до остановки dev-сервера.

Серверные проверки используют реальные тела Edge Functions с внедрёнными зависимостями HTTP/SQL; production-БД не затрагивается. См. [официальный подход Supabase к тестированию функций](https://supabase.com/docs/guides/functions/unit-test).

## Графика

Использованы оба GIF пользователя, оригиналы сохранены как `opening-source.gif` и `waiting-source.gif`. Цветная подложка удалена покадрово, анимация открытия — один цикл 9 кадров, ожидание — бесшовный ping-pong 16 кадров с исходной длительностью кадра. Нормализованы неподвижное основание и нижняя опорная точка; в ожидании движется только центральная область кристалла, внешние металлические части зафиксированы. Есть `closed.png` и `open.png`, а также режим reduced motion. Можно заменить URL на GIF/PNG-спрайт без изменений серверного контракта.

На телефоне доступно «нажать карту → нажать Ядро», на ПК — перетаскивание. Панель усилений вынесена в отдельный слой страницы, чтобы не обрезаться границами арены. Для будущих PNG-спрайтшитов есть адаптер `SpriteSheet.js` с rows/columns/frames/frameMs/loop, остановкой и reduced motion; адресация кадров и реальное рисование проверены тестами. Полные скриншоты — `nexus-core-screenshots`.
